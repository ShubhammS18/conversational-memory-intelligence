1 · The Locked Spec (what we are building)

Routing context: This is an existing project moving from completed design and focused prototypes into integrated implementation. The target is a synchronous local Python modular monolith. The current focus is Phase 3 Backend/API implementation; the completed Phase 6 Memory Architecture governs the implementation, and Phase 9 fixed-workload evaluation follows integration. The reusable memory layer is the main system; chatbot and response generation are outside the approved implementation.

Cognitive job: Given a user’s conversation turns, current query, identity, and existing memory history, determine what information is worth retaining and which valid memories should be retrieved into a bounded context, so that future responses use relevant and current information without exposing another user’s data or returning sensitive, stale, or deleted memories.

Inputs: A trusted caller-established RequestContext; validated conversation-turn content and structured semantic fields; a non-empty current query; authoritative memory history from the structured source store; a trusted timezone-aware UTC clock; and approved configuration for admission, ranking, relevance, retention, token budgeting, embeddings, and index metadata. Caller-supplied timestamps are source-event or provenance information only and never control memory creation time, default validity, expiration, or lifecycle decisions.

Outputs: Admission returns an accepted, rejected, or temporary decision with a reason, memory ID and typed record when created, indexing state, retrievability, and supersession information. Retrieval returns an ordered list of authorized eligible memories, lifecycle and ranking evidence, inclusion and exclusion reasons, the final bounded context, tokenizer and token use, budget exclusions, and an explicit no-relevant-memory result. Decision details are available as structured metadata or privacy-safe events so evaluators can reproduce why each memory was admitted, rejected, ranked, included, or excluded.

Decision policy: User isolation, sensitive-data rejection, deletion, expiration, supersession, lifecycle eligibility, and token-budget enforcement are deterministic and override semantic similarity. Probabilistic embedding similarity and relevance ranking operate only after deterministic checks pass. Similar-score ties prefer newer memories, then explicit user statements, then a stable identifier. Uncertain durable admission is rejected or kept temporary, and retrieval returns no memory rather than forcing the nearest candidate.

Autonomy level: The service may validate requests, apply approved admission rules, reject sensitive or low-value input, persist accepted memories, update the derived index, retrieve and rank eligible memories, apply explicit supersession, enforce recorded expiration, and construct bounded context automatically within approved policy.

Human-in-the-loop points: Forgetting begins only after an explicit authorized request. Uncertain supersession, destructive consolidation, overwriting current facts, and uncertain durable conclusions require approval or remain pending. Changes to admission policy, ranking weights, relevance thresholds, token budgets, retention rules, embedding configuration, or other system-wide policy require human approval and a documented configuration or design change.

Failure tolerance: Fail closed whenever identity, ownership, sensitive-data handling, lifecycle eligibility, deletion state, or token-budget enforcement cannot be verified. SQLite is the authoritative source store and FAISS is derived. If SQLite succeeds but FAISS indexing or durable save fails, retain the record as pending or failed, keep it non-retrievable, report that full success was not achieved, and retry or rebuild safely. Partial deletion is never success: an accepted forget request immediately blocks every retrieval path while cleanup remains pending. Partial retrieval is allowed only when it is a safe subset of verified, authorized, lifecycle-valid, within-budget memories.

Trust boundary: The primary boundary is between each authenticated user and every other user’s memories. Identity comes only from the trusted caller context and cannot be overridden by conversation content or request payloads. Every normal storage, retrieval, update, and deletion operation is user-scoped. Conversation text is untrusted and must pass validation, admission, and sensitive-data checks before durable storage. Authentication itself remains outside the memory layer.

Approved during Genesis step G0 (Cognitive Design) via agentic-swe-master. This record defines the implementation boundary; scope expansion requires a separate approved decision.

Phase 12 · Reliability Engineering

Canonical gate: Every outbound call has circuit breaker + timeout + retry with idempotency. Checkpointing strategy allows resumption after crash. No operation has side effects on retry that it didn't have on first execution.
Source: agentic-swe-master/SKILL.md → Phase 12: Reliability Engineering
Scope: There are no remote outbound runtime calls. Local reliability uses transactions, explicit indexing state, write serialization, idempotency, restart persistence, and reconciliation.

Retrying admission with the same (user_id, idempotency_key) returns the same memory ID without creating another SQLite row or FAISS vector. first slice Proof: python -m pytest tests/integration/test_idempotent_admission.py -q.

Authorized forgetting becomes immediately non-retrievable, remains idempotent through partial cleanup failure, and does not reactivate older superseded state. later forgetting milestone Proof: python -m pytest tests/integration/test_forgetting.py -q.
