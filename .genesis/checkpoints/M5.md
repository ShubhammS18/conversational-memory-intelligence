## M5 post-APPROVE human quiz · PASS · 2026-09-07

- Q1 · design decision: Why require explicit `RetrievalIntent.HISTORICAL`, and why
  does omitted intent preserve current retrieval?
  - Human answer: query wording can be ambiguous and inferred intent could expose
    superseded information when current state was wanted; explicit selection avoids
    that error, while default-current preserves the established safe behavior and
    compatibility for existing callers.
  - Assessment: pass · correctly identifies the inference risk, explicit authority
    boundary, safe default, and compatibility impact.
- Q2 · edge case: What happens when an owned indexed superseded record is
  tombstoned, where is it excluded, and which empty outcomes remain distinct?
  - Human answer: deletion overrides historical intent; SQLite excludes the vector
    before FAISS and hydration repeats the rule to close a deletion race. With no
    historical-eligible memories the result is `no_eligible_memory`; eligible but
    irrelevant candidates yield `no_relevant_memory`; relevant candidates excluded
    only by context size yield `budget_excluded`.
  - Assessment: pass · correctly explains tombstone precedence, both fail-closed
    checks, and the three distinct empty-result causes.
- Q3 · change impact: What does historical intent change, and which downstream
  behavior remains identical?
  - Human answer: only lifecycle eligibility changes, admitting consistent owned,
    indexed, non-deleted active and superseded records without current-time validity
    containment. Owner isolation, FAISS search, the explicit `0.50` threshold,
    deterministic ranking, structured outcomes, and complete-block exact context
    budgeting remain shared and unchanged.
  - Assessment: pass · correctly bounds M5 to candidate eligibility and preserves
    every downstream retrieval policy.
